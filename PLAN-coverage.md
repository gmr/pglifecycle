# Coverage plan: silent schema loss, RLS, and PostgreSQL 18

Status: Phases 0 and 1 complete. Phases 2-7 proposed.
Written 2026-09-21.

Every claim below was verified against PostgreSQL 18.4 (the version
`compose.yaml` pins) by creating the object, running `pull`, running
`build`, and reading the rendered SQL out of `pg_restore -f -`.

## The problem in one paragraph

`pull` parses 18 statement kinds (`dispatch()` in `src/ddl/mod.rs`).
Anything else becomes `Statement::Unsupported` and the whole pg_dump TOC
entry goes to `Assembly::remaining`. Before Phase 0, `remaining` was
written only under `--save-remaining`, so without that flag the object
was gone with one `log::info!` line, below the default log level — that
part is now fixed. The rest is not. Several constructs *do* parse but
lose a modifier, so they come back as a **different object**: a `NOT
ENFORCED` check constraint rebuilds enforced, a virtual generated column
rebuilds `STORED`, `UNIQUE NULLS NOT DISTINCT` rebuilds distinct-nulls.
Silent mis-modeling is the worst failure class here, because the project
file looks correct, nothing lands in `remaining`, and the round-trip
gate passes.

## Verified inventory

### A. Parses, but loses meaning (round-trips to a different object)

| # | Construct | Pulls as | Rebuilds as |
|---|---|---|---|
| A1 | `CHECK (a > 0) NOT ENFORCED` | plain check | **enforced** |
| A2 | `NOT NULL a NOT VALID` | plain not-null | **validated** |
| A3 | `FOREIGN KEY ... NOT VALID` | plain FK | **validated** |
| A4 | `UNIQUE NULLS NOT DISTINCT (u1, u2)` | plain unique | **nulls distinct** |
| A5 | `PRIMARY KEY (id, valid_at WITHOUT OVERLAPS)` | plain composite PK | plain composite PK |
| A6 | `FOREIGN KEY (parent, PERIOD valid_at) REFERENCES tp (id, PERIOD valid_at)` | `columns: [parent]`, `references.columns: [id, valid_at]` | **arity mismatch — restore fails** |
| A7 | virtual generated column | `generated.expression` only | `... STORED`, **and no parens — syntax error** |

A7 has two independent defects. `src/build/mod.rs:2192-2196` pushes the
expression verbatim and unconditionally appends `STORED`; PostgreSQL
requires `GENERATED ALWAYS AS (expr)`, and in PG 18 `VIRTUAL` is the
default, which is why pg_dump omits the keyword.

`NOT ENFORCED` applies to `CHECK` and `FOREIGN KEY` only — verified: the
server rejects it on `UNIQUE`, `PRIMARY KEY` and `NOT NULL`
("UNIQUE constraints cannot be marked NOT ENFORCED").
`WITHOUT OVERLAPS` applies to both `PRIMARY KEY` and `UNIQUE`.

### B. Dropped entirely, no model exists

`POLICY` ×2, `ROW SECURITY`, `EXCLUDE` constraint, `REPLICA IDENTITY`,
column `COMPRESSION`, column `STORAGE`, extended `STATISTICS`, `RULE`,
`DEFAULT ACL` (`ALTER DEFAULT PRIVILEGES`), `SECURITY LABEL` (a
`--no-security-labels` flag exists in `src/cli.rs` with nothing behind
it), and identity columns.

The RLS case is a security regression, not just an omission: pull a
database with RLS enabled and policies, build it back, and the restored
database has row security off and no policies.

Identity is the largest single-object loss. pg_dump emits it as a
separate `SEQUENCE` entry —

```sql
ALTER TABLE public.f ALTER COLUMN i ADD GENERATED BY DEFAULT AS IDENTITY (
    SEQUENCE NAME public.f_i_seq START WITH 100 INCREMENT BY 5
    NO MINVALUE MAXVALUE 900 CACHE 20 CYCLE);
```

— and `ColumnGenerated` has only `sequence: Option<String>` and
`sequence_behavior: Option<String>`, so it cannot hold start, increment,
bounds, cache or cycle even once the parse arm exists.

### C. Dropped by `pull`, though `build` and `models` already support them

`AGGREGATE`, `CAST`, `COLLATION`, `CONVERSION`, `TEXT SEARCH
CONFIGURATION`, `PUBLICATION`, `PUBLICATION TABLE`, `EVENT TRIGGER`.
These have `Definition` variants, `dump_*` renderers, and
`schemata/*.yml`. Only the parse side is missing, so each fix is a new
`dispatch()` arm and nothing else.

### D. Reporting and gates

- ~~Unmodeled entries log at `info!`, below the default level.~~ Fixed
  in Phase 0.
- ~~`remaining.yaml` is written only under `--save-remaining`, so a flag
  is the difference between lossless and lossy conversion.~~ Fixed in
  Phase 0.
- ~~`deploy` warns about project-side `Change::Undiffable` items but
  says nothing about database-side objects it could not model.~~ Fixed
  in Phase 0.
- `fixtures/schema.sql` has no identity column, no generated column, no
  RLS, no exclusion constraint, so `just round-trip` and
  `just deploy-gates` pass through every defect above.
- `CLAUDE.md` says the gate container is Postgres 17; `compose.yaml`
  pins `postgres:18`.

## Feasibility

`tree-sitter-postgres` 19.0.0-beta.2 already exposes every node kind
needed: `CreatePolicyStmt`, `AlterPolicyStmt`, `CreateStatsStmt`,
`RuleStmt`, `AlterDefaultPrivilegesStmt`, `SecLabelStmt`,
`CreateCastStmt`, `CreateConversionStmt`, `CreatePublicationStmt`,
`CreateEventTrigStmt`, `CreateTransformStmt`; `ConstraintElem` carries
`opt_without_overlaps`, `optionalPeriodName`,
`opt_column_and_period_list` and `opt_unique_null_treatment`;
`ConstraintAttributeElem` carries `kw_enforced` and `kw_valid`;
`ColConstraintElem` carries `opt_virtual_or_stored`; `alter_table_cmd`
carries `kw_row kw_level kw_security`, `kw_force`, `replica_identity`,
`column_compression`, `column_storage` and
`alter_identity_column_option_list`. No grammar work, no new crate.

## Governing invariant

Adopt one rule and let the gates enforce it:

> Every schema TOC entry must be modeled, preserved verbatim, or
> explicitly ignored by documented policy.

That is a stronger contract than "`remaining.yaml` is empty", because it
also covers entries a future PostgreSQL adds.

As implemented in Phase 0, the three dispositions are expressed by where
an entry lands in `Assembly::ingest` rather than by an enum:
*ignored by policy* entries (`Database`, `SearchPath`, `SequenceSet`,
`TableData`, `Encoding`, `StdStrings`) are consumed by their own match
arms; *modeled* entries reach the parser and an `Assembly` collection;
*preserved* entries fall through to `remaining` and now fail the
command. Roles, users, groups and tablespaces are ignored by policy for
`deploy` specifically — they are cluster-level and listed in `SKIPPED`
(`src/deploy/diff.rs:129`).

If a descriptor ever needs to be ignorable *after* reaching the parser,
that is the point to introduce an explicit `Disposition` enum; until
then it would restate the match arms.

## Phases

Ordered by risk, not effort: the safety rail first, then failing
fixtures, then output that does not restore, then silent corruption,
then RLS, then parity, then new object families.

### Phase 0 — Make the loss impossible to miss — **DONE**

Decided by the user: `pull` fails when anything is unsupported.

1. `remaining.yaml` is written whenever anything is unmodeled
   (`src/pull/writer.rs:93`). `--save-remaining` is now a hidden no-op:
   a flag must not be the difference between lossless and lossy.
2. `pull` fails by default, after writing the project, with a message
   naming the count, the descriptors, the file, and the override
   (`report_unmodeled` in `src/pull/mod.rs`). Every unmodeled entry
   also logs one `WARN` naming `DESC namespace.tag`, up from `info!`.
3. `--allow-unsupported` downgrades the failure to a single WARN
   summary.
4. `deploy`'s `report()` now also warns about database-side
   `Assembly::remaining` entries, which are absent from the diff
   entirely and were previously unmentioned.

Verified: `pull` of the probe schema exits 1 and names all 8
descriptors; `--allow-unsupported` exits 0; `fixtures/schema.sql` exits
0 and writes no `remaining.yaml`. Three regression tests in
`tests/pull.rs`; `just check`, `just round-trip` and `just deploy-gates`
all pass. Documented under "Unsupported dump entries" in
`docs/commands.md`.

**Two deliberate simplifications from the plan above.** The
`Disposition` enum was not needed: `Assembly::ingest` already consumes
every non-schema descriptor (`Database`, `SearchPath`, `SequenceSet`,
`TableData`, `Encoding`, `StdStrings`) in explicit match arms, so
nothing that is ignorable by policy ever reaches `remaining` — a
non-empty `remaining` already means exactly "unsupported schema". The
enum would have been a second, redundant expression of the same
classification. Add it if and when an entry needs to be ignorable
*after* reaching that point. Likewise the `project.yaml` marker was
dropped: its only purpose was letting `deploy` report existence-only
objects, and item 4 does that directly from `deploy`'s own snapshot,
without a new field in the project schema.

### Phase 1 — Measure the loss — **DONE**

`fixtures/unsupported.sql` holds every construct from section B and C
except `SECURITY LABEL`, and `bin/coverage-gate` (`just coverage-gate`)
pulls it and compares the entries that reach `remaining.yaml` against
`fixtures/unsupported-descs.txt`, currently 18 lines. The gate fails
whichever way that list changes: a new gap has to be modeled or
recorded, and a fix has to shrink the list and move the construct into
`fixtures/schema.sql`. The list is now the measure of how much schema
the tool drops.

The gate also asserts that `pull` *fails* on that fixture without
`--allow-unsupported`, which keeps Phase 0 honest.

**Three changes from the plan above.**

*`SECURITY LABEL` cannot be in the fixture.* Verified against 18.4:
`SECURITY LABEL ON TABLE t IS 'classified'` fails with "no security
label providers have been loaded" unless the cluster preloads a
provider, and no provider ships with the standard server. The gate
would need a custom image to cover it, so Phase 6.7 has to add its own
coverage instead.

*Fixtures cannot be merged red.* The plan said to add every construct
and let the gates go red first. That works locally but not as a commit:
red gates on `main` block everyone. Section B and C constructs go in
`fixtures/unsupported.sql`, which stays green because the expected list
is checked in. Section A constructs — the ones that parse into the
wrong model — never reach `remaining.yaml` at all, so they cannot be
measured this way; each is added to `fixtures/schema.sql` in the same
commit as its fix, where the round-trip gate's schema diff is the
assertion.

*No catalog assertions.* Verified against 18.4: `pg_dump --schema-only`
text already distinguishes every defect in the A list. A stored
generated column dumps as `GENERATED ALWAYS AS (length(b)) STORED` and
a virtual one as `GENERATED ALWAYS AS (length(b))`, so even the case
that looked most likely to need `pg_attribute.attgenerated` is visible
in the text. `NOT ENFORCED`, `NOT VALID`, `NULLS NOT DISTINCT`,
`WITHOUT OVERLAPS`, `PERIOD`, the RLS statements and the identity
`ALTER` are all emitted literally. The existing text diff is therefore
sufficient, and a second assertion pass over nine catalogs would add
maintenance for no coverage. Revisit if a future defect turns out to
dump identically on both sides.

**The gates now run in CI.** They previously did not: GitHub Actions
ran `cargo fmt --check`, `clippy` and `cargo test` only, with no
PostgreSQL anywhere, which is why these defects survived — the checks
that catch them were opt-in and local. A `gates` job in
`.github/workflows/testing.yaml` runs all three scripts against a
`postgres:18` service container, with the PGDG
`postgresql-client-18` package because pg_dump refuses to dump a
server newer than itself.

### Phase 2 — Output that does not restore (~2 days)

3 of the 7 A-rows produce invalid or materially wrong archives, plus
the two `build` defects Phase 8 found. Fix these first.

1. Wrap the generated expression in parentheses in
   `render_table_column`; record it as deviation **14** in the header
   list of `src/build/mod.rs` and in `tests/build_parity.rs` (A7).
2. `ColumnGenerated.kind: Option<GeneratedKind>` — an enum
   (`Stored` | `Virtual`), not a `stored: bool`, so the YAML reads
   clearly and a future third kind fits (A7).
   **Back-compat:** absent must keep meaning `Stored`, because existing
   project YAML carries no flag and renders `STORED` today. `pull`
   writes the field explicitly from now on. Document in
   `docs/project-format.md`.
3. `period: Option<String>` on `ForeignKey` and `ForeignKeyReference`,
   with a `render_foreign_key` arm emitting `PERIOD x` on both sides
   (A6).
4. Emit foreign keys as their own `ALTER TABLE ... ADD CONSTRAINT
   <name> FOREIGN KEY ...` entries after the tables, instead of inline
   in `CREATE TABLE`. Inline FKs cannot express a circular reference,
   and 8 of pagila's 23 tables fail to restore because of it — see
   Phase 8. This also restores the constraint name, which the inline
   form drops. Do this one first: it is a total restore failure on
   ordinary schema, and it changes where item 3's `PERIOD` clause is
   rendered.

### Phase 3 — Silent semantic corruption (~2 days)

One commit per row. Each touches `src/ddl/table.rs`,
`src/models/table.rs`, `src/build/mod.rs`, the matching `schemata/*.yml`
and `fixtures/schema.sql`. `deploy` needs no new comparison logic: the
diff normalizes `Definition` to JSON, so a new optional field is picked
up once it round-trips.

1. `not_valid: Option<bool>` on `CheckConstraint`, `ForeignKey`,
   `NotNullConstraint`, `ColumnNotNull` (A2, A3).
2. `enforced: Option<bool>` on `CheckConstraint` and `ForeignKey` only
   (A1) — the server rejects the attribute elsewhere, so adding the
   field to `ConstraintColumns` would model an impossible state.
3. `nulls_not_distinct: Option<bool>` on `ConstraintColumns::Detailed`
   and `Index` (A4).
4. `without_overlaps: Option<String>` on `ConstraintColumns::Detailed`,
   holding the trailing column name, wired for **both** `primary_key`
   and `unique_constraints` (A5). `ConstraintColumns` is an untagged
   enum, so the bare-name and bare-list forms keep parsing.
5. Identity columns: add `Statement::AddIdentity { table, column,
   behavior, sequence_options }` plus an `alter_table_cmd` arm for `ADD
   GENERATED ... AS IDENTITY (...)`, merged onto the already-ingested
   column the way `SetColumnDefault` is, including the `deferred_*`
   replay path, and suppress the standalone `Sequence` object pg_dump
   emits for it. Extract the option fields shared with
   `models::Sequence` (`data_type`, `increment_by`, `min_value`,
   `max_value`, `start_with`, `cache`, `cycle`) into a
   `SequenceOptions` struct and nest it under `ColumnGenerated` — the
   two existing string fields cannot carry them. A merge whose table or
   column was never assembled must fail loudly, not fall through to
   `remaining`.

### Phase 4 — RLS and policies (~3 days)

Model policies as **children of `Table`**, following the
index/trigger/constraint precedent, not as a new top-level object type:
pg_dump tags them `<table> <policy>`, policy names are unique only
within a table, and `deploy` can reuse `named_pairs()`
(`src/deploy/alter.rs:540`) without a new project directory,
`READ_ORDER` slot, `ObjectKey` or dependency edge.

1. `src/models/table.rs`: `row_level_security: Option<RowLevelSecurity>`
   (`enabled`, `forced`) and `policies: Option<Vec<Policy>>` (`name`,
   `command` including `ALL`, `permissive`, `roles` including `PUBLIC`,
   `using`, `with_check`, `comment`). Place both after `triggers` so
   serde key order stays additive. An omitted `with_check` must stay
   distinguishable from an explicit one.
2. **Absent means unmanaged.** `None` for either field means the project
   predates the feature and `deploy` must leave the database's row
   security alone; `Some` with an empty list or `enabled: false` means
   explicitly managed as empty or disabled. Deserializing absent as
   "disabled, no policies" would turn every existing project into an
   instruction to strip protections. New pulls always write both
   explicitly. A later schema version can make them required.
3. `schemata/policy.yml`, referenced from `schemata/table.yml`.
4. `src/ddl/`: `CreatePolicyStmt`, `AlterPolicyStmt`, and
   `alter_table_cmd` arms for `ENABLE` / `DISABLE` / `FORCE` /
   `NO FORCE ROW LEVEL SECURITY`.
5. Route `COMMENT ON POLICY` to the owning policy in
   `src/pull/mod.rs:1082` — the one defect that already emits a
   user-visible WARN (`Comment on unmatched object: POLICY ...`).
6. `src/build/mod.rs`: emit `ROW SECURITY` and `POLICY` TOC entries
   from `dump_table`, as indexes already are.
7. `src/deploy/`: policies live inside the table but must **not**
   collapse into one indivisible table change. Each reconciles and is
   reported under its own label — `POLICY public.accounts.read_own` and
   `ROW SECURITY public.accounts` — so the script and the warnings name
   the policy, not just the table.
8. **Destructive classification.** Non-destructive and always included:
   enabling RLS, forcing RLS, adding a policy, narrowing one. Gated:
   `DROP POLICY`, `DISABLE ROW LEVEL SECURITY`, `NO FORCE ROW LEVEL
   SECURITY`, broadening a policy's roles, and flipping restrictive to
   permissive. Deciding whether an edited `USING` expression broadens
   access is not decidable in general, so treat **any** policy
   expression change as security-sensitive rather than a plain alter.

   Withholding a `DROP POLICY` leaves the database *more permissive*
   than the repo — the opposite of how the gate protects data
   everywhere else. The emitted script must say so rather than stay
   silent. Open question below: does that warrant a flag separate from
   `--allow-drop`?

RLS must already make `pull` fail (Phase 0) before this lands, so that
the window where policies are silently dropped closes first.

### Phase 5 — `pull` parity with `build` (~1.5 days)

Add `dispatch()` arms for `DefineStmt` (aggregate, collation, text
search parser/dictionary/template/configuration), `CreateCastStmt`,
`CreateConversionStmt`, `CreatePublicationStmt` +
`AlterPublicationStmt`, and `CreateEventTrigStmt`. Models, renderers and
schemata already exist, so each arm is a parse plus an `Assembly` push.
Include publication column lists and row filters, and event-trigger
enabled state.

→ verify: pull a database containing all seven; `remaining.yaml` is
absent, and `just round-trip` passes with them in `fixtures/schema.sql`.

### Phase 6 — New object models (~4 days, ranked)

Do now, in this order:

1. `EXCLUDE` constraints — common, currently dropped without trace. New
   `TableConstraint::Exclude` plus an `exclude_constraints` field
   carrying the access method, element/operator pairs and `WHERE`.
2. `REPLICA IDENTITY` — dropping it silently breaks logical
   replication. One optional `Table` field.
3. `DEFAULT ACL` (`ALTER DEFAULT PRIVILEGES`) — security-relevant.
   Identity is (grantor role, optional schema, object class, grantee,
   privileges, grant option); global and per-schema defaults compose,
   so store the declarations, do not normalize them into an effective
   privilege set. `src/build/acls.rs` is the natural home.

Defer until the above land:

4. Column `COMPRESSION` and `STORAGE` — two optional `Column` fields.
5. Extended `STATISTICS` — a **top-level** object, not a table child,
   unlike policies: the name is schema-qualified and the owner is
   independent of the source relation. Carries kinds (`ndistinct`,
   `dependencies`, `mcv`), columns and expressions, `ALTER STATISTICS`
   target, owner and comment; can hang off tables, foreign tables and
   materialized views.
6. `RULE` — event, relation, condition, `ALSO` vs `INSTEAD`, `NOTHING`
   vs one or more commands. A view's internal `_RETURN` rule must keep
   being represented as a view, never emitted as a user rule.
7. `SECURITY LABEL` — a reusable child collection on every
   label-capable model, keyed by provider. Resolve and store the actual
   provider on pull even though SQL lets it be omitted, and honour the
   existing `--no-security-labels` flag.

### Phase 7 — Gates and housekeeping (~1 day)

Four gates, each checking something the others cannot:

1. **Archive coverage** — every schema TOC entry classifies as
   `Modeled`, `Preserved` or `IgnoredByPolicy`. Shipped in Phase 1 as
   `bin/coverage-gate`; this is the gate that would have caught all of
   section B.
2. **Parse coverage** — every supported descriptor reaches the expected
   `Statement` variant and `Assembly` target.
3. **Round-trip** — the existing `pg_dump` text diff, which Phase 1
   showed is sufficient on its own.
4. **Deploy convergence** — project → deploy into a divergent database
   → pull → compare normalized projects → expect no diff. Run every
   destructive case twice: without `--allow-drop` the removal is
   withheld and reported; with it, the deploy converges.

Then correct the Postgres 17 → 18 line in `CLAUDE.md`. (Done in
Phase 1.)

### Phase 8 — A pagila gate (~1 day)

Take the schema from [xzilla/pagila](https://github.com/xzilla/pagila),
the PostgreSQL sample database, and gate the full cycle on it: load
`pagila-schema.sql`, `pull`, `build`, `pg_restore`, and compare
schema-only dumps of source and restored, the way `bin/round-trip`
already does for `fixtures/schema.sql`. Vendor the schema file with
attribution — the author has said we may use it. Schema only: the data
files are 3 MB and 5 MB, and nothing here needs rows.

**Why it earns a phase of its own.** `fixtures/schema.sql` is a schema
we wrote, so it tests what we thought to test. Pagila is 2177 lines
dumped from PostgreSQL 18.0 by someone else, and it independently
reproduces defects from the audit above plus two this plan had not
found. A trial run confirmed all of the following.

It hits, without being written to:

- a **virtual** generated column
  (`rentals_to_breakeven ... AS (ceil(...))`, no keyword) next to a
  **`STORED`** one on the same table — both halves of A7
- `ALTER TABLE ONLY public.country REPLICA IDENTITY NOTHING`
- `CREATE RULE`, `CREATE EVENT TRIGGER`, `CREATE AGGREGATE`
- `RULE public.rental_report _RETURN` — pg_dump breaks a view
  dependency cycle by emitting the view's internal `_RETURN` rule, so
  the caveat in Phase 6.6 has a real example to test against
- a `PARTITION BY RANGE` table, tsvector columns, 23 tables, 11 views,
  a materialized view, 15 triggers, 13 sequences

A `pull --allow-unsupported` of it currently models 53 objects and
leaves 7 entries unmodeled across 5 descriptors: `PROCEDURE` ×2,
`AGGREGATE`, `TABLE` (the replica identity), `RULE` ×2, `EVENT
TRIGGER`.

**Two new defects it found.** Neither is in sections A, B or C above;
both are `build` bugs, and both come from the same line of rendering.

1. **Foreign keys render inline in `CREATE TABLE`, so a circular
   reference cannot restore.** Pagila's `store` references `staff` and
   `staff` references `store`. No topological order exists, so
   whichever way libpgdump breaks the cycle, the inline `FOREIGN KEY`
   clause names a table that does not exist yet. 8 of 23 tables fail,
   and the failures cascade: `pg_restore` reports 45 errors, starting
   `relation "public.address" does not exist` on `CREATE TABLE
   public.store`. pg_dump avoids this by emitting every FK as its own
   `ALTER TABLE ... ADD CONSTRAINT` entry after all tables exist, and
   `build` must do the same. This is the most severe defect found so
   far: it is not a silent loss but a total restore failure, and it
   needs no PostgreSQL 18 feature to trigger — a mutual FK between two
   tables is ordinary schema design.
2. **Foreign key constraint names are dropped.** `render_foreign_key`
   emits `FOREIGN KEY (p) REFERENCES t (id)` with no `CONSTRAINT`
   clause, although the model carries `name`. The name survives only
   when it happens to match what PostgreSQL generates, which is why
   pagila's `city_country_id_fkey` round-trips and a hand-named
   constraint would not. `deploy` reconciles named constraints as
   DROP/ADD pairs by name (`src/deploy/alter.rs:408`), so a dropped
   name also costs in-place reconciliation.

Fixing 1 subsumes 2: a separate `ALTER TABLE ... ADD CONSTRAINT <name>
FOREIGN KEY ...` entry carries the name by construction.

**Sequencing.** The two `build` defects should be fixed in Phase 2,
alongside the other output that does not restore — they belong with it
by severity, and this phase found them. The gate itself lands last,
because pagila also contains `PROCEDURE`, `AGGREGATE`, `RULE` and
`EVENT TRIGGER`, so a full-cycle comparison cannot be green until
Phases 5 and 6 land. Until then pagila can ride in `bin/coverage-gate`
with its own expected list, which measures progress without blocking
it.

**Also new:** `PROCEDURE` is unmodeled. `PROJECT_DIRS` reserves a
`procedures` directory and `constants.rs` has no `Procedure` variant,
so procedures were overlooked entirely rather than deliberately
deferred. Add them to Phase 5, which is already the "pull parity"
phase.

## Effort

Roughly three focused weeks end to end. Phase 0 is a day and
converts every remaining defect — including ones not yet found — from
silent to visible, so it is worth shipping before anything else is
decided.

## Where this plan disagrees with Rhona

Rhona reviewed the findings and the approach. Adopted: the losslessness
invariant and `Disposition` classification, fail-by-default on
unsupported entries, `remaining.yaml` always written, absent-means-
unmanaged for RLS, per-policy diff identity and destructive
classification, `GeneratedKind` as an enum, full identity sequence
options, `WITHOUT OVERLAPS` on `UNIQUE` as well as `PRIMARY KEY`,
statistics as a top-level object, the `_RETURN` rule caveat, and the
four-gate design.

Two recommendations declined:

1. **Policies keyed by name in a map rather than a list.** Rhona's
   argument (name is identity, order is irrelevant, duplicates become
   impossible) is correct on the merits, but every other named table
   child in this project — `indexes`, `triggers`, `check_constraints`,
   `foreign_keys`, `not_null_constraints` — is a list of objects with a
   `name` field. A map for policies alone would be the only
   inconsistent collection in the format, would need its own
   `schemata` pattern, and would read differently from its siblings in
   the same file. Duplicate names are cheaper to reject in
   `project::validate` than to prevent structurally at the cost of
   format consistency. Revisit only if every child collection moves to
   maps together.
2. **Auditing `NOT ENFORCED` across `UNIQUE`, `PRIMARY KEY` and `NOT
   NULL`.** Verified against 18.4: the server rejects all three
   ("UNIQUE constraints cannot be marked NOT ENFORCED"). Only `CHECK`
   and `FOREIGN KEY` accept it, so modeling the attribute more broadly
   would let a project express a state PostgreSQL cannot hold.

Declined: catalog assertions alongside the existing `pg_dump` text
diff. The text diff is cheaper, broader, and does catch a dropped
object, and every defect in the A list dumps differently on the two
sides (see "No catalog assertions" in Phase 1), so the narrower set the
catalog pass was to cover is empty. Revisit if a future defect turns
out to dump identically on both sides.
